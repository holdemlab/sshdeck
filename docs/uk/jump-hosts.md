# Jump-хости

Jump-хост — це проміжний сервер, через який sshdeck дістається до цільового
(аналог `ssh -J` / `ProxyJump`). Наприклад, сервери в приватній мережі видно
тільки через bastion або проксі.

## Як це працює

sshdeck підключається до jump-хоста, просить його відкрити TCP-канал до
наступного сервера і вже **через цей канал** проходить SSH-рукостискання й
авторизацію з цільовим сервером, прямо зі своєї машини.

Що з цього випливає:
- **Кожен хост авторизується окремо, своїм ключем, і всі ключі лежать тільки в
  тебе.** Класти ключ цільового сервера на jump-хост не треба, і там його ніхто
  не побачить.
- Jump-хост бачить лише зашифрований трафік. Shell на ньому не запускається.
- Ключі хостів перевіряються для кожного вузла ланцюжка окремо, у своєму
  known_hosts.
- На jump-хості має бути дозволений TCP forwarding (`AllowTcpForwarding` у
  sshd; за замовчуванням увімкнено).

## Два способи вказати jump

### 1. Посилання на іншу сесію (рекомендовано)

```yaml
jump: infra/proxy
```

Значення `jump` порівнюється з повними шляхами сесій у дереві. Якщо такий шлях
є, для цього вузла беруться **всі налаштування тієї сесії**: host, port, user,
identity, і навіть її власний `jump`. Тобто ланцюжки будуються самі.

Усе успадкування для jump-сесії йде від **її** папки, а не від папки сесії, яка
через неї підключається.

### 2. Рядок `[user@]host[:port]`

```yaml
jump: ops@bastion.example.com:2200
jump: bastion.example.com            # порт 22
jump: admin@[2001:db8::1]:22         # IPv6 у квадратних дужках
```

Такий вузол **не має власних налаштувань**:
- якщо `user` не вказано в рядку, береться user цільової сесії;
- **ключ береться той самий, що й для цільової сесії** (`identity`).

Тому для jump-хоста з іншим ключем використовуй спосіб 1 (див.
[нижче](#різні-ключі-на-jump-і-на-цільовому-сервері)).

Якщо рядок випадково збігається зі шляхом наявної сесії (наприклад, `proxy`, а в
корені є сесія `proxy`), береться сесія.

## Ланцюжок через кілька хостів

Через кому:

```yaml
jump: infra/edge, infra/inner
```

Порядок такий: ти → `edge` → `inner` → цільовий сервер.

Так само ланцюжок виходить, якщо jump-сесія сама має `jump`:

```yaml
- name: infra
  sessions:
    - {name: edge,  host: edge.example.com,  user: jumper}
    - {name: inner, host: 10.0.0.2,          jump: infra/edge}
- name: prod
  jump: infra/inner       # ти → edge → inner → prod/*
```

Цикли (`a` через `b`, `b` через `a`) sshdeck помічає і показує помилку
`jump loop through …`.

Увесь маршрут видно:
- у статус-рядку вкладки: `jumper@edge → user@inner → deploy@web-01`;
- у вкладці під час підключення: `Підключення до … через …` для кожного вузла.

## Різні ключі на jump і на цільовому сервері

Оформи jump-хост окремою сесією зі своїм `identity` і послися на неї:

```yaml
folders:
  - name: infra
    sessions:
      - name: proxy
        host: proxy.example.com
        user: jumper
        identity: ~/.ssh/id_proxy        # ключ для jump-хоста

  - name: prod
    jump: infra/proxy
    identity: ~/.ssh/id_prod             # ключ для серверів у prod
    user: deploy
    sessions:
      - {name: web-01, host: 10.0.10.11}
      - {name: web-02, host: 10.0.10.12}
```

Ланцюжок для `prod/web-01`:

| Вузол | Користувач | Ключ | Звідки налаштування |
|---|---|---|---|
| 1. `proxy.example.com` | `jumper` | `~/.ssh/id_proxy` | сесія `infra/proxy` |
| 2. `10.0.10.11` | `deploy` | `~/.ssh/id_prod` | папка `prod` |

Те саме в UI:
1. На сесії `proxy` натисни `e` і заповни «Файл ключа» `~/.ssh/id_proxy`.
2. На папці `prod` натисни `e`. Jump: `infra/proxy`, Файл ключа: `~/.ssh/id_prod`.

### Чого уникати

```yaml
- name: prod
  jump: jumper@proxy.example.com     # рядок, не сесія
  identity: ~/.ssh/id_prod
```

Тут до `proxy.example.com` sshdeck теж першим запропонує ключ `id_prod`, бо рядок
не має власного `identity`. Це може спрацювати, якщо правильний ключ є в ssh-agent або в
списку `identities` у [налаштуваннях](settings.md): sshdeck пробує їх усі (див.
[порядок](authentication.md#порядок-авторизації)). Але покладатися на це не
варто.

### "Too many authentication failures"

sshd за замовчуванням дозволяє 6 спроб авторизації (`MaxAuthTries`). Кожен
запропонований ключ — це одна спроба. Першим завжди йде ключ сесії (`identity`),
тож якщо він заданий і правильний, проблеми не буде. Вона можлива, коли
`identity` не задано, а в ssh-agent і `identities` разом багато ключів: сервер
закриє з'єднання раніше, ніж дійде до потрібного. sshdeck тоді покаже
`забагато невдалих спроб: … вкажи identity для сесії або use_agent: false …`
(англійською: `too many authentication failures: … set identity for this
session, or use_agent: false …`).

Що можна зробити:
- задати `identity` для сесії (або її папки);
- вимкнути агент у налаштуваннях (`use_agent: false`);
- тримати в агенті менше ключів;
- прибрати зі списку `identities` зайві ключі.

## Тунелі через jump

Тунелі (`L`, `D`, `R`) працюють на з'єднанні з **цільовим** сервером, тобто вже
після всіх jump-хостів. `L 5432:localhost:5432` у сесії `prod/db` дасть доступ до
порту 5432 на самому `prod/db`. Детальніше: [tunnels.md](tunnels.md).
