# Авторизація і known_hosts

sshdeck має вбудований SSH-клієнт (Go, `golang.org/x/crypto/ssh`). Він не читає
`~/.ssh/config` і не використовує `~/.ssh/known_hosts`.

## Порядок авторизації

Для кожного вузла (і jump-хоста, і цільового сервера) sshdeck пробує методи в
такому порядку:

1. **Публічні ключі**, у цьому порядку:
   1. **ключ сесії** (`identity` самої сесії або успадкований від папки);
      для jump-сесії — її власний `identity`;
   2. ключі з **ssh-agent** (`$SSH_AUTH_SOCK`), якщо `use_agent: true`;
   3. ключі зі списку **`identities`** у [налаштуваннях](settings.md),
      по черзі.

   Той самий ключ двічі не пропонується, навіть якщо він є і у файлі, і в
   агенті.
2. **keyboard-interactive**: питання сервера (наприклад, OTP) показуються у
   вкладці, до 3 спроб.
3. **Пароль**: запит `Пароль для user@host:` у вкладці, до 3 спроб.

Якщо жоден метод не підійшов, буде помилка `автентифікація не вдалася (не
підійшов жоден ключ чи пароль)` (англійською: `authentication failed (no key or
password accepted)`).

**Ключ розшифровується, тільки якщо сервер його прийняв.** Серверу спершу
показується лише публічна частина ключа: для формату OpenSSH вона зберігається у
файлі незашифрованою, а для старого PEM береться з файлу `ключ.pub` поруч. Тому
passphrase питається тільки для ключа, який сервер справді готовий прийняти. Інші
зашифровані ключі (наприклад, `~/.ssh/id_ed25519` за замовчуванням) не
відкриваються і нічого не питають.

**Яким ключем вдалося увійти**, видно у вкладці під час підключення:

```
Підключення до acme/dev/proxy (deploy@203.0.113.10:22)…
Пробую ключ ~/.ssh/acme/id_ed25519
Підключення до acme/dev/main (deploy@10.0.0.12:22) через acme/dev/proxy…
Пробую ключ ~/.ssh/acme/id_ed25519
```

Для ключів з агента пишеться `Пробую ключ з агента <коментар ключа>`.

Ключ, який не вдається використати:
- якщо це файл зі списку `identities`, він тихо пропускається;
- якщо це явно вказаний `identity`, у вкладці з'явиться повідомлення
  `Не вдалося використати ключ …` (англійською: `Cannot use key …`) з причиною: файл не знайдено, формат не розпізнано або
  зашифрований PEM без `.pub`.

## Ключі з паролем (passphrase)

Якщо ключ зашифрований і сервер його прийняв, у вкладці з'явиться
`Passphrase для ключа '…':` (англійською: `Enter passphrase for key '…':`).
- Неправильна passphrase: `Неправильна passphrase.` (англійською: `Bad passphrase.`) і повторний запит, до 3 спроб.
- Порожній `enter` пропускає цей ключ.
- Розшифрований ключ запам'ятовується до виходу з sshdeck (якщо
  `remember_passwords` увімкнено), тож passphrase питається раз за запуск. Щоб не
  вводити її навіть після перезапуску, додай ключ в ssh-agent (`ssh-add`).

## Вхід за паролем

Окремо вмикати нічого не треба. Якщо ключа немає або сервер жодного не прийняв,
sshdeck питає пароль прямо у вкладці: `Пароль для user@host:` (англійською: `user@host's password:`), до 3 спроб. Так
само показуються питання keyboard-interactive (наприклад, `Password:` і
одноразовий код). На сервері має бути дозволено вхід за паролем
(`PasswordAuthentication` або `KbdInteractiveAuthentication` у sshd).

Щоб більше не вводити пароль, встанови на сервер свій ключ:
[`ctrl+a k`](#встановлення-ключа-на-сервер-ctrla-k).

## Запам'ятовування паролів (у пам'яті)

Поки sshdeck відкритий, він пам'ятає:
- **паролі**, які сервер прийняв (окремо для кожного `user@host:port`);
- **розшифровані ключі**, тобто passphrase питається один раз за запуск.

Тому перепідключення (`r`), нова вкладка до того ж сервера (`ctrl+a d`) і
проходження через той самий jump-хост вдруге нічого не питають. У вкладці при
цьому видно `Використовую запам'ятований пароль`.

Правила:
- **Нічого не пишеться на диск.** Після виходу з sshdeck усе забувається.
- **Запам'ятовується тільки прийняте.** Пароль потрапляє в пам'ять лише після
  успішного входу. Неправильний не запам'ятовується.
- **Застарілий пароль забувається одразу.** Якщо сервер відхилив запам'ятований
  пароль (наприклад, його змінили), sshdeck забуває його, пише
  `Запам'ятований пароль не підійшов.` (англійською: `Remembered password was rejected.`) і питає новий.
- **Одноразові коди (OTP) не запам'ятовуються ніколи.** Запам'ятовується лише
  питання keyboard-interactive, у якому є слово «password».
- **Вимикається налаштуванням** `remember_passwords: false` (або «Пам'ятати паролі» на
  екрані налаштувань `ctrl+a ,`). Вимкнення одразу стирає все запам'ятоване.

## Встановлення ключа на сервер (`ctrl+a k`)

Робить те саме, що `ssh-copy-id`: дописує твій публічний ключ у
`~/.ssh/authorized_keys` на сервері. Працює через уже відкрите з'єднання, тож
пароль удруге не потрібен.

1. Підключись до сервера (паролем) і натисни `ctrl+a k`.
2. sshdeck шукає ключ: спершу `identity` сесії, потім ключі зі списку
   `identities` у налаштуваннях.
   - **Ключ знайдено:** показуються його тип, відбиток і шлях. `y` встановлює,
     `g` дає створити новий ключ замість цього.
   - **Ключа немає:** sshdeck пропонує створити новий ed25519-ключ у
     `~/.ssh/id_ed25519`; якщо такий файл уже є, то в `~/.ssh/sshdeck_ed25519`.
     Можна задати passphrase (двічі, для перевірки). Порожнє поле означає ключ
     без passphrase. Наявні файли ніколи не перезаписуються.
3. Ключ дописується на сервері в `~/.ssh/authorized_keys`:
   - каталог `~/.ssh` і файл створюються, якщо їх немає (права 700 і 600);
   - наявні ключі лишаються;
   - якщо цей ключ там уже є, нічого не змінюється, і sshdeck так і скаже.
4. Якщо сесія ще не використовує цей ключ, sshdeck запитає
   `Надалі використовувати … для <сесія>?`. `y` прописує його як «Файл ключа» сесії в
   `sessions.yaml`.

Наступне підключення піде за ключем, без пароля. Якщо в ключа є passphrase, вона
спитається один раз за запуск (див. вище).

Обмеження:
- ключ ставиться лише на **цільовий** сервер вкладки; на jump-хост постав
  окремо, відкривши його як сесію;
- на сервері потрібен POSIX-shell (`sh`): підходить будь-який Linux, BSD чи
  macOS.

## Що зберігається на диску

- **Паролі й passphrase на диск не записуються ніколи**: тільки в пам'яті, поки
  працює sshdeck.
- Ключі не копіюються; sshdeck лише читає файли за вказаними шляхами.
  Створюються нові файли тільки на прохання (`ctrl+a k` → новий ключ).
- Пересилання агента (agent forwarding, `ssh -A`) поки не підтримується.

## Введення у вкладці

Усі запити з'являються прямо в терміналі вкладки, як у звичайному ssh:
- `enter` — підтвердити;
- `backspace` — стерти символ;
- `ctrl+u` — стерти рядок;
- `ctrl+c` / `esc` — скасувати підключення.

Пароль при введенні не відображається. Вставити з буфера теж можна.

## known_hosts

sshdeck веде свій файл ключів серверів: `~/.config/sshdeck/known_hosts` (шлях
змінюється в налаштуваннях). Формат той самий, що в OpenSSH: хост, тип ключа,
ключ. Для порту 22 записується `host`, для інших — `[host]:port`. Записується
host так, як він заданий у сесії: ім'я або IP.

### Перше підключення

```
Справжність хоста '10.0.10.11:22' не підтверджено.
Відбиток ключа ED25519: SHA256:89Ii89/ueWZFHKZgw4tLQLUPIBeZD57G1kNuGqCttW….
Продовжити підключення (yes/no, так/ні)?
```

Англійською (`language: en`) той самий запит виглядає так:

```
The authenticity of host '10.0.10.11:22' can't be established.
ED25519 key fingerprint is SHA256:89Ii89/ueWZFHKZgw4tLQLUPIBeZD57G1kNuGqCttW….
Are you sure you want to continue connecting (yes/no)?
```

- `yes` (або `y`, або `так`) — ключ записується у файл, і підключення триває.
- Будь-що інше — підключення переривається (`ключ сервера не підтверджено`, англійською: `host key verification failed`).

Відбиток краще звірити з адміністратором сервера або з виводом
`ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub` на самому сервері.

Для jump-ланцюжка відбиток питається для кожного нового вузла окремо.

### Ключ сервера змінився

Якщо збережений ключ не збігається з тим, що надіслав сервер, sshdeck **не
підключається і нічого не питає**:

```
КЛЮЧ СЕРВЕРА 10.0.10.11:22 ЗМІНИВСЯ (можлива атака посередника).
Сервер надіслав ssh-ed25519 SHA256:…; у /home/you/.config/sshdeck/known_hosts:3 записано …
Видали цей рядок, якщо зміна очікувана
```

Англійською:

```
HOST KEY FOR 10.0.10.11:22 HAS CHANGED (possible man-in-the-middle).
Server sent ssh-ed25519 SHA256:…; /home/you/.config/sshdeck/known_hosts:3 has …
Remove that line if the change is expected
```

Якщо зміна очікувана (сервер перевстановили), видали вказаний рядок із
`known_hosts`, перепідключись (`r`) і прийми новий ключ.

## Keepalive і обрив зв'язку

- Раз на `keepalive` (за замовчуванням 30 с) sshdeck надсилає серверу
  keepalive-запит.
- Якщо сервер не відповідає довше ніж 3 × keepalive, з'єднання закривається.
- Вкладка показує `з'єднання втрачено` (англійською: `connection lost`); `r` перепідключає.
- `keepalive: 0` вимикає цей механізм.

Таймаут підключення (`connect_timeout`, 15 с) рахується окремо для кожного вузла
і стосується лише TCP-з'єднання. Поки ти вводиш пароль, таймер не йде.
